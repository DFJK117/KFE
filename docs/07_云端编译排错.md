# 07 · 云端编译排错记录（GitHub Actions）

> 这份文档只记录**真实发生过**的失败和**实测过**的证据。

## 0. 为什么要云端编译

本机没有 Haxe 工具链。KFE 的补丁在此之前**从来没有被真正编译过** ——
所有断言只能证明"看起来是对的"。云端编译是唯一能证伪这件事的手段。

Runner：`windows-latest`，Haxe `4.1.5`（和 KE 1.8 时代一致）。

## 1. 第 1 次运行：run `36139106406` —— 失败

**结果**：`completed / failure`，耗时 2m39s，死在「安装依赖」。

```
Installing polymod from https://github.com/MasterEric/polymod.git
Error: Could not clone Git repository.
##[error]Process completed with exit code 1.
```

### 1.1 这个 URL 是谁写的

**是原版 KE 1.8 自己写的**，不是我编的。`dist/KFE/.github/workflows/windows.yml.disabled`
（原版 CI，被我改名为 .disabled）第 41 行：

```yaml
haxelib git polymod https://github.com/MasterEric/polymod.git
```

所以这是**上游的依赖地址过期了**，仓库后来没了。

### 1.2 实测：那 6 个 git 依赖现在都还在吗

用 `gh api repos/<owner>/<repo>` 逐个打（本机 curl 到 GitHub 全是 `000`，出不去，
所以走已授权的 gh 通道）：

| workflow 里写的 URL | 实测结果 |
|---|---|
| `uhrobots/faxe` | 301 → **`ashea-code/faxe`**（还在） |
| `MasterEric/polymod` | **404 Not Found** ← 就死在这 |
| `Aidan63/linc_discord-rpc` | 200 存在 |
| `KadeDev/extension-webm` | 301 → **`Kade-github/extension-webm`**（账号改名） |
| `nebulazorua/linc_luajit` | 200 存在 |
| `nebulazorua/hxvm-luajit` | 200 存在 |

### 1.3 polymod 现在在哪

`gh api search/repositories?q=polymod+in:name` → `FunkinCrew/polymod`（212 star）。
进一步验证：`gh api repos/larsiusprime/polymod` → 301 → `FunkinCrew/polymod`。
（polymod 作者是 Lars Doucet，仓库后来转给了 FNF 团队。）

### 1.4 坑：不能直接换成 master

换 URL 不是改个域名就完事。查 `FunkinCrew/polymod` 各 tag 的 `Polymod.hx` 签名：

| 版本 | `scan()` 签名 |
|---|---|
| v1.2 / v1.3.1 / v1.4.3 / v1.6.0 | `scan(modRoot:**String**, ?apiVersionStr, ...)` |
| **v1.8.0（= master）** | `scan(?scanParams:**ScanParams**)` ← 改了 |

而 KE 的 `source/ModCore.hx:96` 是：

```haxe
var modMetadata = Polymod.scan(MOD_DIRECTORY);   // 传的是字符串
```

**用 master 会直接类型不匹配，编译不过。** 所以必须挑旧版本。

### 1.5 挑版本：锁 1.4.3

haxelib 上的发布版实测（`lib.haxe.org/p/polymod/<ver>/` 的 HTTP 状态）：

```
polymod 1.0    -> 404
polymod 1.1    -> 404
polymod 1.2    -> 404
polymod 1.3.0  -> 200
polymod 1.4.3  -> 200
```

（1.0~1.2 只在 git 上有 tag，haxelib 上没有发布包。）

选 **1.4.3**，三条验证：

1. `scan(modRoot:String, ...)` 还在 ✓
2. `typedef PolymodParams` 字段全齐 —— KE 用到的
   `modRoot / dirs / framework / frameworkParams / apiVersion / errorCallback /
   parseRules / ignoredFiles / customBackend` 一个不缺 ✓
3. `PolymodAssetType` 的声明是
   `enum abstract PolymodAssetType(String) from String to String`
   → 所以 `Polymod.listModFiles("IMAGE")` 传字符串是合法的 ✓

### 1.6 顺手修的第二个点

`KadeDev/extension-webm` 301 → `Kade-github/extension-webm`。
git clone 虽然会跟随重定向，但直接写现名，少一个失败点。

### 1.7 顺带确认：faxe 不需要

`Project.xml` 里是 `<haxelib name="faxe" if='switch'/>` —— Windows 平台根本不加载。
而且 haxelib 上查无此库（`lib.haxe.org/p/faxe/` → 404）。
所以保留 `|| true`，装不上不影响。

## 2. 第 2 次运行：run `36141027508` —— 又失败，但换了个地方

polymod 那步过了（commit `1f755d0` 的改动：polymod 换 haxelib 发布版 1.4.3、
extension-webm 改现名 `Kade-github`），倒在了**编译**这一步：

```
haxelib/flixel-addons/4,0,2/flixel/addons/transition/FlxTransitionableState.hx:6
characters 8-79 : Flixel-Addons is not compatible with flixel versions older than 5.3.0
```

### 2.1 真凶：`haxelib run lime setup`

我锁的是 `flixel-addons 2.10.0`，**装进去的确实是 2.10.0**。但后面那条
`haxelib run lime setup`（不带参数）把 current 版本整个顶掉了。

`haxelib list` 的实测输出（**方括号里才是 current，也就是真正会用到的版本**）：

```
actuate:        1.8.7  [1.9.0]          ← 我要 1.8.7
flixel:                [4.9.0] 6.2.0    ← 侥幸没事（6.2.0 是依赖装的，没抢 current）
flixel-addons:  2.10.0 [4.0.2]          ← 我要 2.10.0
flixel-ui:      2.3.3  [2.6.5]          ← 我要 2.3.3
hscript:        2.0.7  [2.7.0]          ← 我要 2.0.7
hxcpp:          4.2.1  [4.3.2]          ← 我要 4.2.1
lime:           7.9.0  [8.3.2]          ← 我要 7.9.0
openfl:         9.1.0  [9.5.2]          ← 我要 9.1.0
polymod:               [1.4.3]          ← 对
```

`lime setup` 会装一整套「推荐套件」（box2d / layout / systools / flixel-demos /
flixel-tools / flixel-templates…），**而且装最新版、并把 current 指过去**。

**而我给它加了 `|| true`，把这件事完全掩盖了** —— 装依赖那步显示成功，
炸的是 3 分钟后的编译，错误信息还跟真因毫不相干。这是个教训。

### 2.2 顺带验证的两个东西

- `ndll/Windows/` 里只有 `.gitignore` → extension-webm **没有**预编译产物，必须 rebuild
- 但 `libs/Windows/vpx.lib` 是**现成的**（已提交的 blob）→ 不需要 libvpx submodule，
  所以 `haxelib git` 不递归拉 submodule 也没关系
- 实测这一步**通过了**（第 2 次 run 里 `重编 extension-webm` 是 ✓）

### 2.3 修复（commit `6dbfb93`）

```diff
- haxelib run lime setup flixel || true
- haxelib run lime setup || true
+ # 版本守卫：装完立刻校验 9 个关键库的 current 版本，对不上就 exit 1
```

三件事：

1. **删掉两行 `lime setup`** —— 编译根本不需要，Project.xml 声明的库都已显式安装
2. **加版本守卫** —— `haxelib list | tee haxelib-list.txt`，然后逐个比对 current 版本，
   对不上就 `::error::` + `exit 1`。以后再被顶掉，**立刻**在装依赖这步发现，
   不用等到编译 3 分钟后看一条误导性的报错。
   守卫的提取逻辑已用上面那份真实输出在本地验证过：
   `flixel-addons`→`4.0.2`（会报错）、`flixel`→`4.9.0`（通过）、`polymod`→`1.4.3`（通过）
3. **cache key 换成 `haxelib-v2-...`** —— 旧缓存里存着被顶上去的那批版本，强制重建

### 2.4 关于「补丁到底通过编译没有」

**没有。** 第 2 次的报错是 Haxe **编译期**错误（`#error`），说明它在 Haxe 阶段就停了。

（中途我看到 artifact 里有 `obj/ApplicationMain.rc`，一度以为"Haxe 阶段过了"——
**这个结论是错的**，那个 `.rc` 是 lime 生成项目阶段的产物，不是编译成功的证据。
补丁的编译验证到此为止仍然**没有落地**。）

## 4. 怎么自己复核

```bash
gh run list --repo DFJK117/KFE --limit 5
gh run view <run-id> --repo DFJK117/KFE
gh run view <run-id> --repo DFJK117/KFE --log-failed     # 只拉失败步骤（约 5 分钟，39 万行）
```

失败时 CI 会自动上传 artifact `KFE-build-logs`（含 `export/release/windows/haxe/log.txt`），
那是定位 Haxe 编译错误的唯一来源。
