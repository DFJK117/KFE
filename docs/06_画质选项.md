# 06 · 画质选项（渲染后端 / 动态模糊）

## 0. 这一篇要解决什么

需求原话：「再加一些画质选项在 kfe 中，dx11？！，动态模糊？！」

动手之前先把一件事说清楚，因为这里最容易糊弄人：

> **Lime 7.9.0 里没有 `d3d11` 这个渲染后端。**
>
> 做一个「DX11 ☑」的开关、往里传 `--window-render-type=d3d11`，是**假的** ——
> 那个值会被 Lime 丢掉，什么都不会发生。

真实情况是：Windows 上走 D3D 的那条路叫 **ANGLE**，在 Lime 里的参数值是
`opengles`。下面把证据摆出来。

---

## 1. 取证：`render-type` 到底接受什么值

全部来自 `openfl/lime @ 7.9.0`，快照在 `reference/lime/`。

### 1.1 枚举里没有 d3d11

`src/lime/graphics/RenderContextType.hx`：

```haxe
@:enum abstract RenderContextType(String) from String to String
{
	var CAIRO = "cairo";
	var CANVAS = "canvas";
	var DOM = "dom";
	var FLASH = "flash";
	var OPENGL = "opengl";
	var OPENGLES = "opengles";
	var WEBGL = "webgl";
	var CUSTOM = "custom";
}
```

8 个值。**没有 d3d11，没有 d3d9，没有 directx。**

### 1.2 参数怎么流进去

`src/lime/system/System.hx:425-521` 的 `__parseArguments()`：

```haxe
case "render-type", "renderer":
    attributes.context.type = argValue;        // 字符串直接赋给 context.type
case "hardware":
    attributes.context.hardware = __parseBool(argValue);
```

而 `RenderContextAttributes` 里 `type` 的类型是 `RenderContextType`
（`@:optional var type:RenderContextType;`），底层就是个 String。
传一个 Lime 不认识的字符串 → native 层匹配不上 → 回落到默认后端。

**结论：传 `d3d11` 是无效的。**

### 1.3 但 Windows 确实走 D3D —— 走的是 ANGLE

Lime 仓库自带 `dependencies/angle/`：

| 文件 | 大小 |
|---|---|
| `d3dcompiler_47.dll` | 3,466,856 B |
| `libegl.dll` | 133,632 B |
| `libglesv2.dll` | 3,372,032 B |

`d3dcompiler_47.dll` 是 **Direct3D 的 HLSL 着色器编译器**，
`libEGL.dll` / `libGLESv2.dll` 是 ANGLE 的两个核心库。
GLES 调用经 EGL → ANGLE → 转译成 D3D11。

**结论：Windows 上 `--window-render-type=opengles` 就是走 D3D11。**

### 1.4 参数会不会被忽略

`System.hx:464`：

```haxe
if (#if lime_disable_window_override false && #end StringTools.startsWith(parameter, windowParamPrefix))
```

只有定义了 `lime_disable_window_override` 才会整段跳过。
KFE 的 `Project.xml` **没有**定义它 ⇒ `--window-*` 参数生效，
而且会**覆盖** `Project.xml` 里 `<window ...>` 的同名属性。

（`Project.xml:23` 只写了 `hardware="true" vsync="false"`，没有 `render-type`。）

### 1.5 一个必须知道的坑：bool 只认小写 "true"

`System.hx:524`：

```haxe
@:noCompletion private static inline function __parseBool(value:String):Bool
{
	return (value == "true");
}
```

`"True"` / `"1"` / `"yes"` 全部按 **false** 处理。

### 1.6 全量参数表

`System.hx:466-513` 里 `--window-` 前缀后能接的键：

| 键 | 类型 | 落到 |
|---|---|---|
| `render-type` / `renderer` | string | `context.type` |
| `render-version` / `renderer-version` | string | `context.version` |
| `hardware` | bool | `context.hardware` |
| `vsync` | bool | `context.vsync` |
| `antialiasing` | int | `context.antialiasing` |
| `colorDepth` | int | `context.colorDepth` |
| `depth` / `depth-buffer` | bool | `context.depth` |
| `stencil` / `stencil-buffer` | bool | `context.stencil` |
| `fullscreen` / `borderless` / `resizable` / `maximized` / `minimized` / `hidden` / `always-on-top` / `allow-high-dpi` | bool | 窗口属性 |
| `width` / `height` / `x` / `y` / `background` | int | 窗口属性 |
| `fps` | — | **源码里是 TODO，没实现** |

## 2. 所以「渲染后端」选项长什么样

三个真实可用的档，外加一个不传参的 auto：

| UI 显示 | 传的参数 | 实际发生什么 |
|---|---|---|
| `Auto` | （不传） | 用 `Project.xml` 的默认 |
| `OpenGL` | `--window-render-type=opengl` | 走驱动原生 OpenGL |
| `Direct3D 11 (via ANGLE)` | `--window-render-type=opengles` | EGL → ANGLE → D3D11 |
| `Software (no GPU)` | `--window-hardware=false` | 不走 GPU，软件光栅，最慢但最兼容 |

UI 上**不写裸的「DX11」**，写 `Direct3D 11 (via ANGLE)` —— 因为它确实是 D3D11，
但中间隔着一层转译。把这件事说清楚，比喊口号有用。

### 2.1 后端是启动期决定的，只能重启

`__parseArguments` 在窗口创建**之前**跑，读的是 `Sys.args()`。
已经跑起来的进程没法热切换后端。

所以交互设计成：

- 左右切换 → 写进 `FlxG.save`
- 描述里写明需要重启
- **按一下（press）就用新参数重启进程**
- UI 同时显示「你选的」与「当前进程实际在跑的」——两者不一致时一眼能看出来

「当前实际后端」是直接问 Lime 要的，不猜：

```haxe
lime.app.Application.current.window.context.type   // RenderContext.type:RenderContextType
```

见 `src/lime/graphics/RenderContext.hx`。

### 2.2 重启怎么实现

`KFEGraphics.restartWithGraphicsArgs()`：

1. `Sys.programPath()` 拿自身 exe 全路径
2. `Sys.args()` 拿原参数，**剔除**旧的 `--window-render-type=` /
   `--window-renderer=` / `--window-hardware=`
3. 拼上新的渲染参数
4. `Sys.setCwd(exe 所在目录)` —— 不设的话新进程找不到 `assets/`，会白屏
5. `FlxG.save.flush()` 把设置落盘，否则重启后读到的还是旧值
6. `new sys.io.Process(exe, args)` 拉起新进程，`Sys.exit(0)` 退掉自己

## 3. 动态模糊

### 3.1 先说清楚它**不是**什么

**它不是物理正确的运动模糊。**

真正的 motion blur 需要**帧历史**：保留上一帧的深度 / 速度缓冲，
按每个像素的屏幕空间速度反向采样若干帧做时间轴累积。
flixel 4.9 + OpenFL 9.1 这条管线拿不到速度缓冲，
`FlxCamera` 也不把上一帧的 GPU 纹理开放给用户 shader。

做出来的是业界常见的**廉价近似**：把每个像素沿「屏幕中心 → 该像素」
的径向方向拖出一串偏移采样再加权平均。视觉上是「镜头高速推拉的拖影」，
观感接近，物理上是假的。**所以文档里写「近似」，不写「运动模糊」。**

### 3.2 四档

| 档位 | 强度 | tap 数 |
|---|---|---|
| `off` | 0 | — |
| `low` | 0.020 | 6 |
| `medium` | 0.045 | 12 |
| `high` | 0.080 | 20 |

### 3.3 着色器写法（有据可依）

照抄的是 **KE 1.8 自带的 `source/WiggleEffect.hx`** —— 一个活的、带 uniform
的 `FlxShader` 范例。它证明了这套依赖下可用的写法：

```haxe
class XxxShader extends FlxShader
{
	@:glFragmentSource('
		#pragma header
		uniform float uXxx;
		void main() { gl_FragColor = texture2D(bitmap, openfl_TextureCoordv); }')
	public function new() { super(); }
}
```

关键三条：

1. **必须是编译期常量字符串**（`@:glFragmentSource('...')`）。
   只有这样 flixel 的 macro 才能解析出 uniform 并生成 `uXxx.value` 访问器。
   运行时才赋值的字符串做不到 —— KE 自带的 `ModchartShader` 就是那种写法，
   所以它**没有** uniform 访问器。
2. `#pragma header` 由 flixel 展开，提供 `bitmap`（sampler2D）与
   `openfl_TextureCoordv`。采样用 `texture2D(bitmap, uv)`，
   **不是** flixel 的 `flixel_texture2D`。
3. GLSL ES 1.0 要求 `for` 循环有**编译期常量上界**，循环内可以动态 `break`。
   所以写成 `for (int i = 0; i < MAX_TAPS; i++) { if (i >= n) break; ... }`。

> 顺带一个发现：KE 1.8 的 `source/LuaShader.hx` **整个文件是被注释掉的**
> （首行 `/*`、末行 `*/`，里面还有 `samplerXX`、裸 `iResolution` 这种语法错误）。
> 也就是说 KE 的「Lua 自定义 shader」功能是个**半成品**，从来没跑起来过。
> 这也是这里不复用它、而是照 `WiggleEffect` 重写的原因。

### 3.4 挂载点

`PlayState.hx:204` 的 `camGame` 是 `private`，跨类够不到。
所以由 PlayState 自己在 `create()` 里登记（PS-5 补丁，插在
`FlxCamera.defaultCameras = [camGame];` 之后）：

```haxe
KFEGraphics.registerCamera(camGame);
```

挂 `camGame` 而不是 `camHUD` ⇒ **背景和角色模糊，谱面与 HUD 保持清晰**。

### 3.5 一个差点写错的地方：FlxCamera 没有 filters 读接口

最初的实现想「读出相机已有的 filter，把我们的追加进去，不踹掉别人的」。
看起来讲究，其实**编译不过**。

`reference/flixel/FlxCamera.hx`（flixel @ 4.9.0）：

| 行 | 内容 |
|---|---|
| 419 | `/** Internal, the filters array to be applied to the camera. */` |
| 421 | `var _filters:Array<BitmapFilter>;` ← private，无访问器 |
| 305 | `public var filtersEnabled:Bool = true;` ← 只有这个可读 |
| 1496 | `public function setFilters(filters) { _filters = filters; ... }` |

`setFilters()` 是**替换**语义，`_filters` 读不到。

改成自己记账（`blurAttachedTo`）。`setFilters` 的替换语义顺带保证了幂等：
反复调用只会重建数组，不会像 `addFilter` 那样堆叠。

**这条已经写成自动化断言**（`apply_kfe_patch.py` 的校验 2）：

```python
must('KFEGraphics 没有读 cam.filters（FlxCamera 无此接口，去注释后检查）',
     'cam.filters' not in strip_for_count(kf))
```

以后再有人想这么写，跑补丁器的时候就会被拦下来。

### 3.6 会不会踹掉 modchart 的 filter

理论上是替换语义、会踹。实际上撞不上：

- `ModchartState.hx` 只往 `camNotes` / `camSustains` 挂 wiggle
- 我们只挂 `camGame`

两台不同的相机。这一点写在这里，不藏着。

## 5. 已知局限（诚实清单）

1. **动态模糊是单帧近似**，不是帧历史累积。上面重复了三遍，是因为它重要。
2. **渲染后端切换要重启进程**，没有热切换。UI 已写明，并提供一键重启。
3. **`uAspect` 只在挂载时设一次**。运行中把窗口拖成别的比例，径向校正会有偏差。
   重新切一下选项即可修正。
4. **重启依赖 `Sys.programPath()`**。在 `lime test windows` 这种由启动器托管的方式下
   拿到的可能不是目标 exe；打包成独立 exe 后正常。
5. **全部未经过真实编译**（开发机没有 Haxe 工具链）。
   所有静态校验只能证明「看起来是对的」，CI 才是唯一裁判。
